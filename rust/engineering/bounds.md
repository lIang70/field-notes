# 有界容器（上限 / 回收 / 观测）

> 一个常驻守护进程最典型的死法是"内存随运行时间线性增长"，而代码里每一处都"看起来没问题"。
> 案例来自 flowcraft 的 `rust/`（MIT），以及它的一次自查：把 crate 里所有容器按"有没有上限"过了一遍。

## TL;DR

- **无界容器要三件套**：上限（配置可见）+ 回收策略（谁、何时）+ 观测（暴露当前值）。只加上限会变成 DoS 型拒绝，只加回收会变成"不可解释地丢数据"。
- **"按过期剪枝"比"记全量历史"便宜**：撤销表只记到该条授权本来就会失效的那一刻，于是内存与**活跃**授权成正比，而不是与历史成正比。
- **剪枝要放在有界节奏上，不是每次写**：每次 `issue` 都扫一遍过期项，就把 O(n) 放到了"每次续租"的路径上。
- **注册表没有上限，通常不是 bug 而是产品语义缺失**：进程退出后客户端还能读多久？这个问题没人回答，代码里自然就没有回收。
- **Go 与 Rust 两棵树里同一类容器往往只有一棵有界**。查"有界覆盖率"要两边一起查，否则换个实现就复发。

## 1. 真实存在的上限（flowcraft Rust 侧）

| 常量 | 值 | 守的是什么 |
| :--- | :--- | :--- |
| `MAX_PATH` | 4096 | 用户给的路径长度上限，防拼装爆内存 |
| `MAX_HEAD` | 16 KiB | 代理 / 协议头部读取上限（超出即断） |
| `MAX_BYTES` | 1 MiB | 单个 secret 文件的读取上限 |
| `DEFAULT_BYTES` | 256 KiB | telemetry ring 的字节预算（`0` 表示不限） |
| `MAX_KEYS` | 4096 | 单个映射的键数 |
| `MAX_CREATED` | 65536 | 一次扫描里"新建路径"的记账条数 |
| `MAX_GAPS` | 16 | 区间合并时的碎片上限 |
| `MAX_INTERVAL` | 1 h | 定时器周期上限，防"配置写错变成永不触发" |
| `LIVE_GRANTS_PRUNE_AT` | 1024 | 活跃授权超过它才扫一次过期项 |

> 这张表的共同点：**每个都不是"性能参数"，而是"没有它就会出现一个明确的故障模式"**。写常量时把那个故障模式写进注释，比写"最大值"有用。

## 2. 撤销表：按过期剪枝

授权是 Ed25519 签名、可离线校验的短时令牌（所以平台不是数据路径上的单点）。撤销只在本地生效，那么"撤销记录"要活多久？答案是**活到它本来就会失效的那一刻**：

- 被撤销的 grant 记到它的 `exp`；
- 被撤销的 session 记到它最后一个 grant 的 `exp`；
- 读、写时都顺手剪枝，所以内存 ∝ 活跃授权，而不是 ∝ 服务过的 run 数。

工程上的两个细节：

- **剪枝节奏要有界**：`LIVE_GRANTS_PRUNE_AT = 1024`，超过才扫一轮。注释里写了理由——"sweep on every issue 会把 O(n) 放到每次续租的路径上"。
- **时钟可注入**：`Clock = Arc<dyn Fn() -> SystemTime>`，过期逻辑才能被测试；否则只能靠 `sleep` 测过期。

## 3. 会话注册表：上限还是语义？

同一个 crate 里的 session registry 是 `Mutex<BTreeMap<id, Entry>>` + 代际计数 + `watch` 通知，**没有上限**。

自查时的判断是：这不是"忘了加 `MAX`"，而是**产品没定义"进程退出后客户端还能读多久"**。定义清楚之前加上限，只会把"该保留多久"变成"随机拒绝"。真要加，形态是：

- 上限按"活跃会话数"还是"内存字节"？
- 超限时是拒绝新会话，还是回收最老的（且回收后 `list` 怎么解释）？
- 观测：暴露"当前会话数 / 上一次回收时间 / 回收数"三个数。

## 4. 三件套怎么落地

```text
上限        const MAX_X / settings.max_x，配置里可见、越界报错
回收策略    谁触发（读、写、定时）、回收什么（最老、过期、最不常用）
观测        当前值 + 累计丢弃/回收次数，进指标而不是进日志
```

缺一不可：

- 只有上限 → 达到上限后新请求被拒，用户看到"随机失败"。
- 只有回收 → 数据"偶尔消失"，无从解释。
- 没有观测 → 线上只能等 OOM 才发现。

## 5. 反模式

- `Vec::push` 在请求路径上，注释写"不会太长"。
- 用 `HashMap<_, Vec<_>>` 记"每次调用的历史"，从不裁剪。
- 上限写成一个魔数散在三个文件里，改一处忘两处。
- 观测只暴露"当前值"，不暴露"回收了多少"——看不出策略有没有在工作。
- 只在 Rust 侧加上限，Go 侧同构的那份忘了。

## 6. 清单

- [ ] 每个常驻容器的上限有名字、有注释（说明防什么故障）
- [ ] 回收策略明确：谁触发、回收谁、回收后语义
- [ ] 观测：当前值 + 回收/丢弃计数
- [ ] 剪枝不在热路径上做 O(n)
- [ ] 双树都查过（Go 与 Rust 同构的那份）
