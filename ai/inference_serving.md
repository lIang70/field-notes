# 自建推理服务（容量 / 部署 / 运维）

> 讲模型选定之后的那部分工作。选型和质量评测在 [评测](evals.md)。
> 内部业务的数字只留比例和延迟量级，价格绝对值、供应商名、集群标识都去掉了。

## TL;DR

- **自建推理的难点是容量账和运维账**，选型只占一周。剩下全是起不来、抢显存、挂载崩、资源不传播、并发一压就断。
- **规划卡数不能用批量吞吐上限**。按吞吐算是 11 张卡，按首包延迟算是 15 张，多出来的 35% 是"不让用户等"的成本。
- **启动期能自检的都写进入口脚本**：GPU 真建一次上下文、每卡显存合计校验、挂载试写、变量拼写点名告警。
- **性能数字要绑版本**。换镜像后旧延迟数据自动作废，报告里得写"复测前不要对外引用"。
- **并发不是越高越好**。单路 RTF 超过 1 流式播放就跟不上：并发 32 时 1.09（临界），64 时 1.86。

## 1. 成本账和容量账

成本侧只留比例：自建单位成本约为供应商协议价的三分之一，省 68%。但协议价本身是深度折扣（牌价两折），不续约时成本会放大五倍左右。真正的风险敞口在商务，不在技术。

所以结论是分层而不是替换：自建承担主力，商业 API 承担溢出和降级。留一套能随时切回去的小集群，本身就是这笔账的一部分。

容量侧，单卡 24GB 档 GPU 的实测：

| 并发 | 吞吐（音频秒/秒） | 首字节 | 单路 RTF | 用途 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | — | 0.40s | 远小于 1 | 空载基准 |
| 16 | ~27 | 0.96s | ~0.6 | 交互推荐区间 |
| 32 | ~31 | 1.58s（未限流）/ 0.99s（ramp 后开播） | 1.09 | 临界，播放开始卡 |
| 64 | 35.7 | — | 1.86 | 只适合离线批量 |

从 1 到 64，吞吐涨 6.4 倍，单请求延迟涨 8 倍。交互场景建议并发 8–16，不是配置默认的 64。

加 ramp（攒够 100ms 音频就开播）之后，"可开播"降到 0.14 / 0.37 / 0.54 / 0.99s（并发 1/8/16/32），代价是吞吐降 6%。

算卡数时先用"需求音频秒/月 ÷ 单卡可用音频秒/秒"，再按首包延迟上调。拿批量压测的数字去规划会很乐观——用户感知的是首包。

## 2. 启动期自检

```text
entrypoint
  ├─ GPU：可用性 + 真建一次上下文（只数 device_count 会放过"在但用不了"）
  ├─ 显存：每卡 gpu_memory_utilization 合计 ≤ 1（多 stage 共卡必须启动前拦）
  ├─ 挂载：试写 + 离线模式变量（只读挂载缺 HF_HUB_OFFLINE 直接 EROFS）
  ├─ 变量：未识别的前缀要点名告警（拼错是最常见的"改了没生效"）
  ├─ 超时：区分"慢"和"死"（冷启放宽，GPU 不可用要快速失败）
  └─ 降级：某张卡不可用就退单卡，不是整体失败
```

几个具体做法：`SVC_DEPLOY_CONFIG=auto` 按可见 GPU 数选档，避免手工档位在换卡型时必然错；`SVC_CONFIG_OVERRIDES` 支持新增键（`+` 前缀）和数组值。

就绪语义别只看进程活着。推理可用、资源（音色库之类）非空，才算 ready。

## 3. 资源同步

多副本共享一份可写资源时，先对齐"比什么"：

- 下行比较用 key + ETag，不比 mtime、不比 size。同名资源换内容不传播，根因几乎都是比较维度不对。
- 删除要防误删：HEAD 确认，再两轮确认。对账脚本真的误删过。
- 对象前缀和文档、日志一起对齐。少一个斜杠这种 bug 只有真机暴露。
- 同步要有收敛测试，不然"看起来同步了"是常态。

## 4. 做过的优化

| 优化 | 实测 | 备注 |
| :--- | :--- | :--- |
| 图桶 batch `[1,2,4,8]` | 同吞吐下 P95 −17~18% | 首版 OOM 是内存账算错，不是桶不对 |
| ramp（攒 100ms 开播） | 可开播延迟降 37%~65%（并发 32 最差，只有 −37%） | 吞吐 −6%，权衡清楚 |
| 限流到并发 32（入口排队）+ ramp | TTFP P95 0.65s | 与上表"未限流同并发 1.58s"不是同一口径；尾巴在建连，不在推理 |
| 双卡 4090 同实例 c128 | 109~113 音频秒/秒 | 与单卡 A10 不同硬件，不能直接比倍数；得一起调 fd 上限（ulimit 是隐藏前提） |
| codec 批量解码 | 曾被切成 batch=1 逐条 replay | 靠逐请求统计发现，不看统计会一直怪模型 |

调不动的时候先看逐请求统计和显存账，再动参数。

## 5. 踩到的坑

- `--gpu-memory-utilization 0.9` 覆盖了配置里 per-stage 的 0.3，单 stage 独吞近 20 GiB 直接 OOM。去掉后显存回落 10 GiB。命令行参数和配置文件谁优先，必须写进文档。
- 基础镜像 GB 级，跨地域拉取能到小时级。要么预同步到同地域仓库，要么接受首次发布很慢。
- 流式短文本并发下约 1% 的 `IncompleteRead`：响应头已发、音频推到一半被服务端中断。非流式 0%。前端要能按"已产出部分"续，不能整段重来。
- 权重上传要有分片级续传、传前体检、分片 ETag 复核。几十 GB 一把梭必然断在半路。
- 仓库改名和集群资源名（Namespace / Deployment / 镜像名）要解耦，别为了整洁去动线上对象。
- 旧方案下线留书面归档（`docs/archive/` 加原因），否则半年后没人敢删代码。

## 6. CI 的边界

CI 全离线、无 GPU、无网络、秒级：格式检查（版本锁在 `package.json`）、离线回归、静态检查。凭证一律假实现，不打网络。

静态检查能兜住一大类事故：shell / Python / YAML / 文档链接 / K8s 清单 / 环境变量与默认值 / 权重清单 pin。

需要真机的验证单独列清单：镜像构建、真机延迟与质量冒烟、固定 N 条回归 prompt。写清"CI 不覆盖这些"，比假装覆盖安全。

还有一条不是技术问题但会卡死流程：required check 的 context 就是 workflow 里的作业名。改作业名必须同步改分支保护规则，否则所有 PR 卡在 "Expected — Waiting for status to be reported"。
