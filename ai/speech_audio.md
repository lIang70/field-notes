# 语音与音频链路（实时 + 离线）

> 两条线：实时对话语音（RTC → ASR → LLM → TTS）和离线批处理（VAD → 说话人分离 → ASR → 声纹身份）。
> 服务侧容量账在 [自建推理服务](inference_serving.md)，评测方法论在 [评测](evals.md)。

## TL;DR

- **实时语音的稳定性死在 teardown**，不死在识别率。native SDK 关闭顺序错了会 wedge 整个进程，重连逻辑救不回来。
- **归一化放在入口**：远端音频统一 16kHz 单声道，下游谁都不用再猜采样率。
- **声纹阈值必须随聚合语音量分档**。同一套 embedding 上，达到 EER 的阈值会从 0.09 漂到 0.67，固定阈值必然在某个档位失效。
- **评测口径要先自证**。collar 排除写错，会让"同一份参考、不同系统去掉的时长不同"，两次评测根本不可比。
- **误差主要来自重叠语音，不是聚类**。换后端（DER 20.79% → 6.54%）比调阈值有用得多。

## 1. 实时链路

```text
客户端 → RTC（第三方引擎）→ 服务端解码 → 归一化 16kHz mono
      → 流式 ASR → LLM 流式生成 → TTS → RTC 下行
```

踩出来的几条：

- 引擎工厂做单实例，teardown 加硬化：关闭顺序加超时兜底，不允许"等某个 native callback 回来"。
- 归一化在入口做，线性插值重采样到 16k mono。
- SSE 和 WS 并存时要两阶段回调激活，否则事件重复下发。
- 心跳挂在 stream ctx 上，流断了自然停；独立 ticker 一定泄漏。
- 识别器的输出 pipe 绑 ctx，不绑就有一批 goroutine 在取消后还活着。
- 可观测性统一走 telemetry，同一个请求要能串起来。

## 2. 语音之外的结构

- 叙事（scene）和情绪（story）是两个正交层，混在一个 prompt 里会互相污染输出格式。
- 生成内容的语言按 locale profile 解析，不要硬编码单语言。
- 人格用 OCEAN 漂移建模，漂移要有上界和回归力，否则长会话会漂成另一个角色。
- 长会话靠分层注入 + 时间衰减，注入位置比注入量更重要（见 [上下文工程](context_engineering.md)）。

## 3. 离线流水线

10 个阶段，全部可断点续跑：

```text
① decode       ffmpeg → 16kHz mono
② vad          silero 流式扫描（按 60s 分块读 + 逐帧喂，内存恒定）
③ partition    用 VAD 空隙切块（切点必落在语音空隙，不切词）
④ diarize      逐块独立分离（默认带分割模型的后端，可换声纹聚类基线）
⑤ consolidate  跨块合并同一人 + 说话人级向量
⑥ chunk        按说话人轮次切小音频块
⑦ asr          OpenAI 兼容接口（vLLM / SGLang），mock 后端离线测链路
⑧ identity     manual / voiceprint（ECAPA 192 维 + 库检索 + 双阈值三态）
⑨ eval         RTTM 读写 + NIST 定义 DER（含最优说话人映射）+ 重叠探测
⑩ merge/emit   去重、SRT / VTT
```

三个结构性选择：块内独立、跨块聚合（否则内存随文件长度线性涨）；阈值定在聚合向量上（块级向量太短，噪声大）；留一个 mock 后端，让链路正确性和模型效果能分开验证。

## 4. 结果

| 数据集 | 分离后端 | 本项目评分器 | pyannote.metrics（含重叠） | 剔除重叠 |
| :--- | :--- | :--- | :--- | :--- |
| AMI 全量 16 场（8.9h 真实会议，未知人数） | 带分割模型 | 6.54% | 14.71% | 8.71% |
| AMI 全量 16 场 | 声纹聚类（无需授权） | 20.79% | 31.27% | 23.20% |
| VoxConverse dev×30（166min） | 带分割模型 | 1.77% | 3.97% | 2.94% |
| VoxConverse dev×30 | 声纹聚类 | 4.45% | 7.98% | 5.46% |

三套评分器下排名和倍数关系一致（默认后端好 1.9~3.2 倍），所以差异不是评分口径造出来的。

自有评分器对重叠段更宽松：VoxConverse 差约 2pp，AMI 差约 8pp（AMI 重叠多得多）。这个差异写出来比藏起来可信。

## 5. 声纹身份

```text
matched    分数 > 高阈值            绑定已知身份
ambiguous  低阈值 ≤ 分数 ≤ 高阈值   待人工确认，不自动绑定
unknown    分数 < 低阈值            新人物，进待审核队列
```

双阈值是 open-set 的标准做法，单阈值在边界必然抖。阈值不能拍一个 0.5：先定能接受多高的误接受率，再反推。

实测更麻烦的一点：阈值要跟聚合语音量挂钩。同一模型上，达到 EER 的阈值随语音量单调上移（0.09 → 0.67），所以工程上得按语音量分档标定，而不是全局一个值。库规模上到十万级要上 ANN，而近似检索会带来额外误识别，阈值得重标。

还有一个容易骗自己的场景：注册音频和测试音频是同一段时，相似度能测到 0.99。那是训练集泄漏，不是识别能力。评测集必须和注册集物理隔离。

## 6. 评测踩过的坑

1. collar 排除不准。旧实现只在 ref/hyp 边界上切区间、拿中点猜是否落在 collar 里，导致同一份参考、不同系统去掉的时长不同（同一批数据两套后端差 5.7 分钟）。修法是把 collar 边界也放进时间点集合。
2. 数据不全就开始对比。会议音频跨多个分片，旧脚本只下第一片，某场少 41% 语音，DER 12.8%；补齐后 5.74%。旧对比表里那一行不可比。
3. 重叠探测被当测量值。重建结果对象时漏了字段导致重叠恒为 0；修好后总量偏差 −13%，但单场从 −57% 到 +37%。只能当"哪里大概有重叠"的信号。

## 7. 真实瓶颈

- "不知道说话人数"是算法级难点，不是工程级。已知人数时聚类能调得很好，未知时阈值就崩。
- 重叠语音是主要误差源，该上带分割模型的后端（注意授权条款），而不是继续调阈值。
- 链路跑通不等于产品可用。API、队列、DB、对象存储、部署是另一半工作量，缺一块就只是个能跑的脚本。
- 合成 TTS 样本（无混响、无底噪、无重叠）测出的 DER 0% 是乐观下界，不能当能力宣传。
